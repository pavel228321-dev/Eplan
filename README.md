# EplanCipMvp — MVP автогенерации страниц "Состав ПЛК" для проекта 1364

Пять проектов в решении:

- **EplanCipMvp.Core** — чтение xlsx-спецификации + группировка сигналов по модулям ET200SP.
  Не зависит от EPLAN, только от NuGet-пакета ClosedXML.
- **EplanCipMvp.Core.SelfTest** — консольная утилита, чтобы проверить Core **без EPLAN**.
- **EplanCipMvp.App** — сама интеграция с EPLAN API. Требует установленной EPLAN.
- **EplanCipMvp.Gui** — десктопный интерфейс (WinForms) поверх `App`.
- **EplanCipMvp.Web** — тот же функционал через браузер (11.09.2026, см. раздел
  ниже) — запускается локально на той же машине, где стоит EPLAN, WinForms
  не заменяет, а дополняет.

## Шаг 1 — проверить Core без EPLAN (можно сделать прямо сейчас)

> **Быстрый вариант, без Visual Studio:** `EplanCipMvp.SelfTest.Ready.zip` —
> уже собранный `.exe` (Release, .NET Framework 4.8) со всеми зависимостями
> рядом. Распаковать и запустить `EplanCipMvp.Core.SelfTest.exe <путь_к_xlsx>`
> прямо из командной строки. Собран и **реально прогнан** (через Mono, прямо
> в контейнере разработки) на настоящем файле 1364 — числа ниже сверены не
> "в теории", а по фактическому выводу программы.

1. Открыть `EplanCipMvp.sln` в Visual Studio 2022 (нужен .NET Desktop workload).
2. Собрать решение — NuGet сам подтянет ClosedXML.
   Если `EplanCipMvp.App` не собирается из-за отсутствия сборок EPLAN — это нормально
   на этом шаге, можно временно выгрузить его из решения (правой кнопкой → Unload Project)
   и собрать только `EplanCipMvp.Core` + `EplanCipMvp.Core.SelfTest`.
3. Запустить `EplanCipMvp.Core.SelfTest.exe` с путём к вашему файлу:
   ```
   EplanCipMvp.Core.SelfTest.exe "C:\путь\1364-Сводная_специфкация_изделий.xlsx"
   ```
4. Сверить вывод со **следующими числами** (НЕ с листом "2. Сигналы по шкафам" —
   там устаревшие цифры, см. врезку ниже):
   - ШРП‑1: DI 6 модулей, DO **4**, AI 3, AO 1
   - ШРП‑2: DI 4, DO 3, AI 2, AO 1
   - ШУ: DI 2, DO 1, AI 2, AO **0 (отсутствуют)**

   Если числа совпали — логика группировки верна, переходим дальше.
   Если нет — пришлите мне вывод программы и текст ошибки, поправлю.

   > **Найденное расхождение в исходном файле.** Программа читает лист
   > "Перечень устройств" (детальный, 178 строк) — так и должно быть, сам файл
   > в примечании к листу "2" говорит: *"для единообразия мы принимаем
   > распределение по перечню"*. Но листы "1. Сигналы (факт)" и "2. Сигналы по
   > шкафам" ещё не пересчитаны под это решение. Конкретно: 5 насосов M1
   > (`L1M1`…`L5M1`, DonJoy, частотник) в "Перечне устройств" помечены
   > `DI:0 DO:0 AI:0 AO:0` с типом канала "Полевой (PN)" — то есть управляются
   > по Profinet, без дискретных/аналоговых каналов. А в листах "1" и "2" эти
   > же насосы всё ещё считаются как "1 DO + 1 AI + 1 AO" на каждый — отсюда и
   > расхождение (лишние 5 AO в ШУ, лишние 3 DO в ШРП‑1). Стоит уточнить у
   > того, кто вёл файл, какой вариант верный, и привести все три листа
   > к одному значению.

## Шаг 2 — подключить EplanCipMvp.App к реальной EPLAN

**09.09.2026: этот шаг больше не "вслепую".** Раньше `Program.cs`/`PlcPageBuilder.cs`
были написаны по общей документации eplan.help и никогда не компилировались. Теперь
сигнатуры **подтверждены** по реальным сборкам вашей EPLAN 2.9 (файлы
`Eplan.EplApi.*u.dll` + XML-документация, которые вы прислали) — и весь `EplanCipMvp.App`
**реально скомпилирован** здесь же (0 ошибок), с этими самыми сборками в качестве ссылок.
Что поменялось по факту (не предположение — из дизассемблирования и XML-докладов):

- Сборки называются не `Eplan.EplApi.ApplicationObject`/`Base`/`DataModel`/`HEServices`,
  а `Eplan.EplApi.Baseu`/`DataModelu`/`HEServicesu` (суффикс "u" = Unicode-сборка),
  плюс появились `Systemu` (там теперь `EplApplication`) и `Starteru` (`AssemblyResolver`).
- `new Project(path)` — **в принципе неправильно**: конструктор `Project` всегда
  бросает `NotImplementedException` (это написано в его собственном XML-документе).
  Открывать проект нужно через `new ProjectManager().OpenProject(path)`.
- `EplApplication.Init(...)` принимает `(string strApplicationModifier, bool, bool)`,
  а не массив строк. Перед вызовом обязательно нужен `AssemblyResolver.SetEplanBinPath(...)`
  и `app.EplanBinFolder = ...` — иначе, по документации, `Init` падает.
- `Project.Save()` не существует — модель EPLAN транзакционная, закрывают через `Close()`.
- `Main` теперь помечен `[STAThread]` — офлайн-приложения обязаны быть однопоточными
  (COM), это было явно написано в докладах и раньше отсутствовало.
- `Insert.PageMacro(string, Page, Project, bool)` — сигнатура подтверждена
  дизассемблированием, не изменилась по сути от первоначальной догадки.

Что делать вам:

1. В `EplanCipMvp.App\EplanCipMvp.App.csproj` поправить `HintPath` на реальную папку
   `Bin` вашей установки (обычно `C:\Program Files\EPLAN\Platform\Bin\` — проверьте
   точное имя папки у себя, может отличаться).
2. Скопировать `appsettings.Local.json.example` → `appsettings.Local.json`, прописать
   реальные пути (проект, xlsx, макросы) — см. «Настройки» ниже.
3. Собрать в Visual Studio. Учитывая, что здесь собралось чисто — скорее всего, соберётся
   и у вас. Если всё же будут ошибки — почти наверняка из-за версии/имени сборок,
   не из-за логики.
4. **Единственное, что осталось не реализовано осознанно** — `GetOrCreatePlcPage` умеет
   только найти уже существующую страницу нужного раздела (по `PageStructureId`), но
   не создать раздел/страницу с нуля, если их вообще ещё нет в проекте. Если для 1364
   ещё не создана ни одна страница `ПЛК` под нужный шкаф — создайте вручную одну
   заготовку в EPLAN, дальше вставка макросов пойдёт после неё автоматически.
5. Реальное содержимое макроса модуля (`FillChannelTexts`) — всё ещё ждёт Этапа 0
   (нужно посмотреть эталонный макрос в самой EPLAN).

## Настройки (appsettings.json)

`EplanCipMvp.App` теперь читает конфигурацию вместо жёстко зашитых путей —
задел на реальную интеграцию с EPLAN, не только на сам MVP:

```
EplanCipMvp.App/
  appsettings.json              — базовые настройки, в git/архиве
  appsettings.Local.json        — ваши личные пути (создайте сами из .example, не обязателен к переносу другим людям)
  appsettings.Local.json.example — шаблон
```

Разделы:

- **`Eplan`** — `ProjectPath` (.elk проекта), `MacroBasePath` (куда кладёте макросы
  с Этапа 0), `BinPath` (папка `Bin` вашей EPLAN — теперь **реально используется**
  в рантайме, `AssemblyResolver.SetEplanBinPath`/`EplApplication.EplanBinFolder`,
  не только справочно; ссылки на сборки для КОМПИЛЯЦИИ по-прежнему отдельно в .csproj).
- **`Spec`** — путь к xlsx-спецификации и имя листа (по умолчанию «Перечень устройств»).
- **`PlcHardware`** — факты по реальному оборудованию из спецификации заказа Siemens
  (`1364_01-спец_заказ_Siem`): артикул и описание ЦП (`6ES7515-2AN03-0AB0`, CPU 1515-2 PN),
  предположительный шкаф ЦП (`ШУ` — по названию «Шкаф Управления», не подтверждено
  документом напрямую), артикул интерфейсного модуля ET200SP (`6ES7155-6AA02-0BN0`,
  количество 3 — по одному на шкаф), и `OrderedModuleCounts` — сколько модулей каждого
  типа **реально уже заказано**. Программа теперь при запуске **автоматически сверяет**
  расчёт по актуальной спецификации с этими заказанными числами и печатает предупреждение
  при расхождении (см. ниже про насосы M1 — на момент написания заказ соответствует
  СТАРОМУ расчёту, 15/12/7/4, а не текущему «Перечню устройств», 12/8/7/2).
- **`Grouping`** — то же самое, что раньше было константами в `ModuleGrouper.cs`
  (резерв 20%, порядок типов для нумерации, база нумерации `-A...`) — теперь настраивается
  без пересборки Core.

Аргументы командной строки (`EplanCipMvp.exe <xlsx> <project.elk>`) по-прежнему работают
и перекрывают `Spec.XlsxPath`/`Eplan.ProjectPath` из конфига — удобно для разового прогона
на другом файле без правки json.

## Подпись канала (+LINE1-V0, +MCC1-M1...)

Новое: `NamingSettings` + `ChannelLabelBuilder` — строит подпись канала в формате,
похожем на реальные страницы МСА (`+LINE3-V0 Вода в бачок`), а не голый тег из
xlsx (`L3V0`). Логика: если тег начинается с `L<номер>` — считаем это линией и
подставляем `+LINE<номер>` (шаблон `LineStructureTemplate`); если нет (общие
устройства вроде `M1`, `V21` в шкафу ШУ) — используем `+MCC1`
(`CommonStructurePrefix`, подтверждено и в реальном имени проекта 1260, и в
самой МСА). Проверить можно прямо сейчас без EPLAN — `Core.SelfTest` печатает
примеры. **Это решает только «что писать»** — «как записать в EPLAN» всё ещё
заглушка (`FillChannelTexts`), ждёт Этапа 0.

## Обозначения модулей (-2A1.5, -3A2.10...)

`PlcModule.Designation` заполняется автоматически по схеме
**`-{номер станции}A{цифра типа}.{номер модуля}`**, например `-2A1.5` (станция 2,
DI (цифра 1), 5-й модуль по счёту).

Схема **подтверждена**, а не предположение по 2 картинкам из МСА, как раньше:
09.09.2026 получен настоящий 295-страничный PDF-экспорт проекта **1260**
("Участок хранения молока", тот же исполнитель — **Aprotec Engineering Ltd.**,
Могилев, — что и 1364). В нём видно на 3 полных станциях сразу:

- станция **2A1** (шкаф ET101): DI-модули `2A1.1`…`2A1.11`, разделитель `2GA2`,
  DO-модули `2A2.1`…`2A2.9`, разделитель `2GA3`, AI-модули `2A3.1`, `2A3.2`;
- станция **3A1** (шкаф ET102): DI `3A1.1`…`3A1.14`, DO `3A2.1`…`3A2.10`, AI `3A3.1`;
- станция **1A1** (шкаф E01, здесь же и CPU `1512-1DK01`): DI `1A1.1`…`1A1.3`,
  DO `1A2.1`, `1A2.2`, AO `1A4.1`, `1A4.2` — **цифра типа фиксирована (AO всегда
  "4"), даже когда типа AI в шкафу вообще нет** — значит нумерация НЕ "сквозная
  через все типы", как думали раньше по МСА, а у каждого типа своя постоянная цифра.

Правило номера станции: шкаф, где стоит ЦП, получает станцию **"1"** (не по порядку
в проекте — у 1260 в дереве листов E01 идёт третьим, но станция у него первая);
остальные шкафы — 2, 3... по естественной сортировке имени. Это настраивается через
`ModuleGrouperOptions.CpuCabinet` (= `PlcHardware.CpuCabinet` из `appsettings.json`).

Цифра типа (`TypeDigits`: DI=1, DO=2, AI=3, AO=4) и номер станции для конкретно
**1364** — перенесены по аналогии с 1260, а не подтверждены собственным `.elk`/PDF
проекта 1364. Раз оба проекта делает одна и та же контора с одним и тем же
EPLAN-шаблоном, это гораздо надёжнее прежней гипотезы по МСА (которая, судя по всему,
вообще референс/ТЗ от заказчика, а не рабочий стандарт Aprotec) — но 100% совпадение
всё равно стоит сверить, когда будет доступ к живому проекту 1364.

> Артикулы модулей в 1260 записаны внутренними короткими кодами базы EPLAN
> (`CT-121F`, `CT-222F`, `CT-7220`...), а не сырыми артикулами Siemens `6ES7...` —
> стоит иметь в виду при сверке с заказом.

## Структурный идентификатор страницы (=1.ШРП1.DP...)

Новое: `PageStructureSettings` + `PlcModule.PageStructureId`. Это **не тег устройства**
(тем занимается `NamingSettings`/`ChannelLabelBuilder`, см. выше) — а то, куда сам
**лист** попадает в дереве страниц EPLAN. По образцу 1260 (теперь основной референс
компании, не МСА): там страницы "Состав станции"/"Обзор модулей" лежат под
`=1.ET101.DP`, `=1.ET102.DP`, `=1.E01.DP` — идентификатор строится как
`={номер}.{код шкафа}.{код подгруппы}`, код подгруппы для страниц ПЛК — `DP`
(Distributed Periphery).

Для 1364 подставили свои имена шкафов вместо ET101/ET102/E01 —
`=1.ШРП1.DP`, `=1.ШРП2.DP`, `=1.ШУ.DP` (`CabinetCodes` в `PageStructureSettings`,
дефисы убраны — EPLAN такое не любит). **Важно:** это два РАЗНЫХ ортогональных
факта — тег устройства для 1364 всё равно остаётся в стиле МСА (`+LINE1-V0`,
потому что 1364 организован по линиям мойки, как и МСА, а не по бакам, как 1260) —
а вот структура СТРАНИЦ берётся по образцу 1260, раз он теперь основной референс.
Как и обозначение модуля, номер станции/код шкафа для 1364 конкретно не подтверждён
собственным файлом — перенесено по аналогии.

## Обвязка ПЧ (VfdCircuit, первый узел в работу)

Новое: `VfdComponentDefaults` + `VfdCircuitBuilder`. В отличие от `ArticleResolver`
(TBD-гипотезы) — это **реально заказанный** состав силового контура на каждый
насос с ПЧ, взято из спецификаций заказа 1364 (`1364_03_спец_заказ_НКУ`,
`1364_04-спец_заказ_ПЧ`, см. `docs/1364-order-specs.md`):

- ПЧ: Danfoss VLT Micro Drive `FC-051P11KT4E20H3BXCXXXSXXX` (11 кВт) — **⚠️ в
  спецификации явно указано, что серия снята с производства**, уточнить перед заказом.
- Панель управления `LCP12`.
- Автомат защиты двигателя Schneider `GV3P32` + доп. контакты `GVAN11`
  (для диагностики состояния силовой цепи по ПО).

`VfdCircuitBuilder.BuildAll(devices)` берёт все устройства с
`BaseDeviceType == "Насос центробежный с ПЧ"` (в реальном файле 1364 их 5 —
`L1M1`…`L5M1`) и собирает на каждый одинаковый набор компонентов. Это данные
для отрисовки листа "обвязка ПЧ" в EPLAN по образцу 1260 (Program.cs печатает
чек-лист, веб-превью показывает карточки) — сам лист программа не рисует.

## Порядок каналов внутри модуля

Каналы сортируются **естественной сортировкой** по тегу (`L1V2` раньше `L1V10`) —
см. `NaturalStringComparer.cs`. Раньше порядок зависел от порядка строк в xlsx;
теперь он детерминирован независимо от файла. Присвоение тега конкретному месту
в конкретном модуле (не только порядок) пока не сверялось с реальной инженерной
логикой распределения — это тоже стоит проверить на Этапе 0.

> **10.09.2026: нашёлся реальный механизм — не через простой индексатор.**
> Разобрал сборку `monodis`'ом (не только доки): `Function` наследует
> `FunctionBase`, у которого подтверждены в IL публичные `get_NameParts`/
> `set_NameParts` (тип `FunctionBasePropertyList`) — то же самое, что у
> `Page`/`PAGE_COUNTER` (тоже read-only через простой индексатор, но
> переименование возможно через `NameParts`). В `FunctionBasePropertyList`
> подтверждены (тоже по IL) сеттеры `FUNC_PREFIX`/`FUNC_CODE`/`FUNC_COUNTER`.
> По докам `FUNC_PREFIX`: *"you receive a DT '4K5' with the digit '4' as the
> prefix"* — видимый тег = PREFIX+CODE+COUNTER. Теперь переименование делает:
> ```csharp
> function.NameParts = new FunctionBasePropertyList { FUNC_PREFIX = targetPrefix };
> ```
> Только `FUNC_PREFIX` (номер линии насоса), не трогая `CODE` (`QF`/`U`/`M`) и
> `COUNTER` (его уже раздаёт сам EPLAN через `NumerationMode.Number` при
> копировании, без коллизий) — и только на `IsMainFunction`. Компилируется
> против реальных сборок (0 ошибок) — но **не подтверждено живым тестом**,
> ждём следующего прогона.

## 11.09.2026, поздно вечером: браузерный интерфейс (EplanCipMvp.Web)

Пользователь попросил интерфейс через браузер вместо WinForms-окна — с явным
уточнением (через уточняющий вопрос): открывать браузер будут ТОЛЬКО с той
же машины, где стоит сама EPLAN (не по сети, не из интернета). Значит
аутентификация/шифрование не нужны — это просто более удобный UI поверх той
же самой, уже готовой логики, не распределённая система.

**Архитектура**: сама EPLAN — десктопная COM-программа, "перенести её в
браузер" невозможно и не нужно. Браузер — это пульт: HTTP-запросы идут на
маленький локальный сервер (`EplanCipMvp.Web.exe`, слушает только
`http://localhost:5177/`, без прав администратора не требуется, т.к. это не
`+`/`*`, а именно `localhost`), а сервер уже дёргает ровно ту же логику
(`VfdPageCopier`/`DeviceGroupPageCopier`/`PlcModulePageCopier`), что раньше
вызывалась из `MainForm.cs`. `EplanCipMvp.Gui` (WinForms) не тронут вообще —
остаётся рабочим запасным вариантом.

- `EplanSession.cs` — то же состояние, что раньше жило в полях `MainForm`
  (`_app`/`_lockingStep`/`_projectManager`/`_sourceProject(2)`/`_targetProject`),
  плюс однопоточная очередь задач (`BlockingCollection<Action>` + выделенный
  STA-поток) — EPLAN требует STA и один живой сеанс, а HTTP-запросы приходят
  на пуле потоков, поэтому все вызовы EPLAN API сериализуются через эту
  очередь. Методы `CopyVfdPumps`/`CopyDeviceGroup`/`CopyPlcModules` — дословный
  перенос одноимённых методов `MainForm.cs`, просто вместо `Log(...)` на
  текстовое поле — `Action<string> log`.
- `ApiServer.cs` — `System.Net.HttpListener` (часть net48, NuGet не нужен),
  3 JSON-эндпоинта (`/api/connect`, `/api/groups/{key}/donor-pages`,
  `/api/copy`) + раздача статики из `wwwroot/`. JSON — через
  `System.Web.Script.Serialization.JavaScriptSerializer` (тоже часть net48,
  `Reference Include="System.Web.Extensions"`, без NuGet).
- `wwwroot/index.html` + `app.js` — фронтенд без фреймворка, 1:1 повторяет
  сценарий `MainForm` (пути → "Подключиться" → чекбоксы групп → донор-страница
  на группу → "Скопировать" → лог). Пути к файлам — просто текстовые поля
  (браузер не имеет доступа к диалогу выбора файла с реальным диском на той же
  машине так же, как WinForms `OpenFileDialog`).
- `Program.cs` — запускает сервер и сразу открывает браузер (`Process.Start`)
  на `http://localhost:5177/`.

**Грабля при сборке**: `ConfigurationBuilder().SetBasePath(...)` в
`CopyPlcModules` не резолвился — оказалось, `using Microsoft.Extensions.Configuration;`
не был подключён (extension-методы не находятся через полное имя типа без
`using`, даже если сборка сама подключена). Плюс транзитивный
`PackageReference` на `Microsoft.Extensions.Configuration.*` через
`ProjectReference` на `App` в этом проекте не сработал так же гладко, как в
`Gui` — добавлены те же 3 пакета явно в `EplanCipMvp.Web.csproj`.

Собрано (`dotnet build`, 0 ошибок), архив `EplanCipMvp.Gui.Ready.zip` теперь
содержит оба варианта — WinForms в корне, `EplanCipMvp.Web.exe` + `wwwroot/`
в подпапке `Web/`. Не запущено живьём — как и всегда в этом проекте, первый
реальный тест на машине пользователя может вскрыть проблемы (особенно:
получит ли `HttpListener` право слушать порт без прав администратора —
инструкция `netsh http add urlacl` уже в консольном выводе `Program.cs` на
случай отказа).

## 11.09.2026, ночью: реальная находка при перепроверке — TypeLoadException на старте

Пользователь попросил "перепроверить, точно ли всё работает" — до этого момента
весь проект **ни разу не запускался живьём**, только компилировался (см. историю
выше — постоянная оговорка "не проверено живым тестом"). В контейнере разработки
нашёлся `mono` — не настоящая EPLAN, но достаточно, чтобы впервые РЕАЛЬНО
запустить `.exe` и проверить хотя бы то, что не зависит от живого EPLAN
(старт процесса, HTTP-сервер, раздача статики).

**Результат: оба `.exe` (и `Gui`, и новый `Web`) падали немедленно при старте**,
до открытия окна/порта:
```
System.TypeLoadException: Could not load type of field 'MainForm:_app' due to:
Could not load file or assembly 'Eplan.EplApi.Systemu'...
```

**Причина**: поля с EPLAN-типами (`EplApplication`, `LockingStep`,
`ProjectManager`, `Project`) были объявлены НАПРЯМУЮ на `MainForm`/`EplanSession` —
а эти объекты создаются (`new MainForm()` в `Program.cs`, `new EplanSession()`
в `Program.cs` веб-версии) СРАЗУ при старте программы, ДО того, как
`AssemblyResolver.PinToEplan()` вообще успевает сказать рантайму, откуда брать
сборки EPLAN (тот вызывается только внутри `BtnConnect_Click`/`Connect()`, по
нажатию кнопки, когда форма/сессия уже давно созданы). Создание объекта с полем
незагружаемого типа — рантайм пытается резолвить тип поля сразу, падает раньше,
чем доходит до кода, который бы объяснил, зачем.

Это НЕ было заметно раньше просто потому, что раньше никто и не запускал —
чистая компиляция этого не ловит (сборки EPLAN участвуют только как
`<Reference Private="False">`, реально не нужны для компиляции тела метода).

**Фикс** (в `MainForm.cs` и `EplanSession.cs` одинаково): все
EPLAN-типизированные поля вынесены в отдельный маленький класс `EplanState`
(nested, `private class`), который создаётся НЕ в конструкторе/при старте, а
ТОЛЬКО внутри `BtnConnect_Click`/`Connect()`, сразу ПОСЛЕ `PinToEplan()` —
тогда резолвинг сборок откладывается до момента, когда `AssemblyResolver` уже
готов их отдать. Заодно перенесли и `Dictionary<string, List<Page>>`
(`_candidatesByGroup` в веб-версии) — `Page` тоже EPLAN-тип, тот же риск.
Добавлены null-проверки `_eplan == null` в местах, которые могут быть вызваны
ДО первого подключения (например, если пользователь ставит галочку группы
раньше, чем нажимает "Подключиться").

**Проверено по-настоящему** (не только компиляция):
- `EplanCipMvp.Web.exe` под `mono` — стартует, HTTP-сервер поднимается,
  `GET /`, `/app.js`, `/aprotec-logo.svg` отдаются (200), несуществующий путь —
  404. `POST /api/connect` с заведомо неверными путями возвращает чистую
  JSON-ошибку `500` (`"Could not load file or assembly 'Eplan.EplApi.Starteru'"`
  — потому что в контейнере разработки нет настоящей EPLAN, это ожидаемо) —
  **и, главное, процесс НЕ падает целиком**, продолжает обслуживать запросы.
- `EplanCipMvp.Gui.exe` под `mono` + `xvfb-run` (виртуальный дисплей) — стартует
  и висит на цикле сообщений окна (как и положено GUI-программе), никакого
  `TypeLoadException`.

Разумеется, это Mono, не настоящий Windows .NET Framework 4.8 и не настоящая
EPLAN — живой прогон на машине пользователя всё ещё нужен и может вскрыть
что-то ещё. Но сам факт немедленного падения на старте — уже пойман и
исправлен, а не остался бы незамеченным до первого реального теста.

метода целиком, ДО выполнения хоть одной его строки, включая любой try/catch
внутри самого этого метода (это отдельное явление от TypeLoadException на
полях объекта, из-за которого раньше появился класс `EplanState`). Из-за этого
результат подключения (`ConnectResult.Log`) при ошибке подключения к EPLAN
целиком терялся — пользователь получал голый `{"error": "..."}` без единой
строки лога, даже накопленных ДО EPLAN-кода. Исправлено выносом
EPLAN-обращающегося кода в отдельный метод `ConnectToEplan(...)` — тот же
принцип, что уже применялся для `CopyVfdPumps`/`CopyDeviceGroup`/
`CopyPlcModules`. Теперь при ошибке подключения (неверный `BinPath`/путь к
проекту) лог сохраняется целиком, с понятной строкой ошибки в конце — проверено
через `mono EplanCipMvp.Web.exe` + `curl` на заведомо неверных путях.

## 12.09.2026: Шаг 0 (полное копирование донора) + реконсиляция страниц — ПЕРВОЕ действие, которое инструмент УДАЛЯЕТ

Пользователь скорректировал направление: вместо вставки отдельных страниц из
донора в уже созданный пустой целевой проект — сначала копировать донор
ЦЕЛИКОМ (раз схемы CIP-моек и так похожи), а дальше по каждой группе
устройств приводить количество уже существующих (донорских) страниц в
соответствие со спецификацией: где нужно больше — дублировать существующую
страницу внутри проекта; где меньше — **удалять лишние**; везде —
переименовывать теги. Это прямо противоположно моей более ранней рекомендации
не делать голый full copy — но с условием, которое подтвердил пользователь:
без системной реконсиляции full copy воспроизводит ту же проблему, что была у
битой копии коллеги (см. историю переписки/ранние разделы) — поэтому обе части
(копирование + реконсиляция) добавлены вместе, не по отдельности.

**Шаг 0 — `ConnectRequest.CreateTargetAsFullCopyOfDonor1`**: если включено и
файла по пути "Целевой проект" ещё нет — вызывается
`ProjectManager.CopyProject(SourceProject1, TargetProject, CopyMode.Snapshot)`
(найдено через XML-доки `Eplan.EplApi.DataModelu.xml`) ДО открытия каких-либо
проектов. `Snapshot`, а не `All` — единственный режим, описанный в докладах
как неэксклюзивный (не блокирует донора монопольно), тот же принцип, что уже
применяется через `ProjectManager.OpenMode.ReadOnly`. Если файл уже
существует — копирование пропускается, файл просто открывается как есть (не
перезаписываем без явного намерения). Каждое из 4 задокументированных
исключений (`ProjectCopyException`/`ProjectNeedsUpgradeException`/
`IncompatibleDatabaseException`/`ArgumentException`) ловится отдельно, с
понятным текстом в лог.

**Реконсиляция — `EplanCipMvp.App/PageReconciler.cs`** (новый класс): для
каждой группы (сейчас — насосы VFD и группы `DeviceGroupCatalog`, **модули
ПЛК/DP не входят** — см. ниже, почему) находит уже существующие страницы
группы в целевом проекте (переиспользует
`VfdPageCopier.FindCandidateDonorPages`/`DeviceGroupPageCopier.
FindCandidateDonorPages`, они и раньше были написаны как фильтр произвольного
`Project`, не только донора), сравнивает их количество с тем, что реально
нужно по спецификации, и:
- если нужно больше — дублирует ПОСЛЕДНЮЮ существующую страницу через
  `Page.CopyTo(targetProject, ..., NumerationMode.Number, false)` — в докладах
  нет ограничения на то, что целевой проект должен отличаться от текущего
  проекта страницы, то есть "копирование в себя" тем же API разрешено;
- если нужно меньше — удаляет ХВОСТОВЫЕ (после сортировки) страницы через
  `Page.Remove()` — единственный подходящий метод, найден в тех же XML-доках
  (`Project.RemoveAllPages()` — не то, удаляет ВСЕ страницы проекта);
- переименовывает оставшиеся/новые страницы через **`RetagExistingPumpPage`/
  `RetagExistingBatch`** — новые публичные методы `VfdPageCopier`/
  `DeviceGroupPageCopier`, полученные РЕФАКТОРИНГОМ (не переписыванием) уже
  подключённой перетэговки: логика внутри `CopyForPump`/`CopyBatch`, которая
  раньше шла СРАЗУ после `CopyTo` и была завязана на переменную `copied`,
  вынесена в отдельные приватные методы (`RetagPumpPage`/`RetagDeviceBatch`),
  принимающие ЛЮБОЙ `Page` — обычный поток "донор → копирование" не тронут,
  это чистое извлечение (проверено компиляцией, поведение не менялось).

**API — двухфазно**: `POST /api/reconcile/preview` (ничего не меняет, только
считает и возвращает план: сколько есть/нужно, что будет продублировано, **что
будет удалено — отдельным списком**) и `POST /api/reconcile/apply`
(выполняет). В UI кнопка "Применить план" неактивна, пока не нажата "Показать
план" для ТЕХ ЖЕ отмеченных групп, плюс подтверждение через `confirm()` перед
самим удалением — первое разрушительное действие в истории инструмента,
почему-то поэтому лишняя осторожность к месту.

**Почему модули ПЛК (DP) не вошли**: у DP один и тот же фильтр страниц ".DP"
покрывает и титульные листы, и страницы детализации — какая из уже
существующих в целевом проекте страниц титул, а какая деталь, программно
сегодня не различить (это выбирает пользователь вручную при выборе
донор-страницы, не свойство самой страницы). Не гадаем — доработка отдельным
шагом, если понадобится.

**Ещё один найденный по ходу баг — снова JIT-атомарность метода под Mono**:
оказалось, что не только объявление EPLAN-типизированных ПОЛЕЙ объекта валит
JIT (см. историю с `EplanState` ниже) — то же самое происходит, если внутри
ОДНОЙ лямбды просто ЧИТАЕТСЯ свойство `_eplan.TargetProject`/
`_eplan.SourceProject` (это требует резолва ВСЕХ полей вложенного класса
`EplanState`, в т.ч. EPLAN-типов, даже если конкретно это поле — не EPLAN-тип).
Из-за этого `ReconcilePreview`/`ReconcileApply`/`GetDonorPages`/`Copy`,
вызванные ДО первого успешного `/api/connect`, вместо понятного "Сначала
вызовите /api/connect" отдавали голый JIT-эксепшен. Исправлено единообразно:
проверка `_eplan == null` (БЕЗ обращения к его свойствам) — прямо в лямбде,
а весь код, который трогает `_eplan.SourceProject`/`.TargetProject` — вынесен
в отдельный `*Core`-метод, вызываемый только когда `_eplan != null` уже
гарантирован (см. `ConnectToEplanCore`/`ReconcilePreviewCore`/
`ReconcileApplyCore`/`GetDonorPagesCore`/`CopyCore`). Проверено через
`mono EplanCipMvp.Web.exe` + `curl` на все четыре эндпоинта без предварительного
connect — теперь везде чистое сообщение, а не голая ошибка.

**Не проверено живым тестом** (нет живой EPLAN в контейнере разработки) — то,
что реально важно проверить у пользователя, в указанном порядке и **сначала на
тестовой копии проекта, не на боевом файле**:
1. Что `CopyProject(..., CopyMode.Snapshot)` вообще создаёт рабочий,
   открываемый проект.
2. `/api/reconcile/preview` — визуально сверить список "будет удалено" глазами.
3. Только потом `/api/reconcile/apply` — и обязательно сначала на резервной
   копии, `Page.Remove()` необратим.

### Установка: папка программы в Platform\<версия>\Bin (24.09.2026)

По просьбе пользователя вернулись к прежней архитектуре вместо надстройки EPLAN:

1. Распаковать `EplanCipMvp.Gui.Ready.zip` и скопировать папку программы в
   `Platform\<версия>\Bin`, где лежат `Eplan.EplApi.*u.dll`
   (например `C:\Program Files\EPLAN\Platform\2.9.4\Bin`). Можно целиком
   подпапкой: программа ищет `Eplan.EplApi.Starteru.dll` рядом с собой и на
   1–2 уровня выше (`Web\` внутри подпапки тоже находит).
2. Запустить `EplanCipMvp.Gui.exe` (или `Web\EplanCipMvp.Web.exe`) оттуда.
3. В поле «Папка Bin вашей EPLAN» указать папку с `W3u.exe`
   (`Electric P8\<версия>\Bin`), затем проект `.elk` → «Подключиться».

Функции те же: нумерация кабелей (Gui — вкладка, Web — карточка) и
генерация листов из доноров. Если DLL EPLAN не найдены ни рядом с программой,
ни в `Platform`, соседнем с папкой W3u.exe, при подключении выводится
подсказка скопировать папку в `Platform\<версия>\Bin` (`EplanBootstrap.CheckBinPath`).

Проверено под mono (без настоящей EPLAN): программа в
`EPLAN/Platform/2.9.4/Bin/EplanCipMvp/Web` подхватывает Starteru и доходит
до `AssemblyResolver.SetEplanBinPath`; программа вне EPLAN получает подсказку.
Сборка против DLL 2.9 — 0 ошибок, 0 предупреждений.

## Известные ограничения этой версии

- `EplanCipMvp.App` и `EplanCipMvp.Gui` реально скомпилированы (здесь же, против
  ваших сборок EPLAN 2.9) — но **не запущены** живьём (нет доступа к EPLAN
  в контейнере разработки). Логика компилируется, но не гарантированно работает
  на 100% с первого раза — как и было с `Program.cs`/`PlcPageBuilder.cs`.
- `FillChannelTexts` и `GetOrCreatePlcPage` (в `PlcPageBuilder`, путь через вставку
  макроса) — по-прежнему заглушки, ждут Этапа 0. Актуальный путь для обвязки ПЧ —
  `VfdPageCopier` через `EplanCipMvp.Gui`, см. раздел выше, он его не требует.
- Переименование тега устройства после копирования — реализовано через
  `Function.NameParts`/`FUNC_PREFIX` (найдено через IL-разбор сборки, не
  просто по докам), компилируется, но **не подтверждено живым тестом**. См. врезку выше.
- Технологическая часть (P&ID, резервуары) в этот MVP не входит — только страницы ПЛК.
- Обозначения модулей (`-2A1.5`...) подтверждены на реальном проекте 1260 того же
  исполнителя, но конкретно для 1364 — перенесены по аналогии, не из собственного
  файла 1364, см. раздел выше.
