# Генерация номеров потенциалов (31L+, 1M, 1L11...) по обходу вверх до источника — дизайн

Дата: 01.10.2026. Продолжение фичи «Нумерация жил и проводов»
(`docs/superpowers/specs/2026-09-24-wire-core-numbering-design.md`,
`docs/superpowers/specs/2026-09-25-wire-numbering-conflict-resolution-design.md`).
Источник задачи — пункт бэклога №1 (`docs/backlogs/1-генерация-имён-потенциалов-31l-1m-по-трассировке-в.md`).

## Проблема

Правило 3 («Потенциал», `{Потенциал}` в `WireRuleTemplate`) сейчас только копирует
`Pin.Potential`. Если EPLAN отдаёт **generic**-потенциал без номера (`L`, `N`, `M`,
`L+` — см. `WireRuleTemplate.IsGenericPotential`), правило не срабатывает вообще
(подстановка пустая), и провод остаётся без номера, хотя в самом проекте он
однозначно должен называться, например, `1M` или `30L+`. Сейчас это руками не
чинится никаким существующим правилом — нужна новая логика, которая **достраивает
номер**, когда буква уже известна, а числа нет.

## Разбор примеров 1260 (проверено по PDF, два независимых шкафа)

Лист `1260-1.ET101.LV-EFS` (+CP.ET101) и его точная копия `1260-1.ET102.LV-EFS`
(+CP.ET102, устройства с префиксом `-3...` вместо `-2...`) показывают один и тот
же шаблон под разными префиксами DT — это и разрешает неоднозначность: номер в
имени потенциала **не зависит от префикса шкафа**, это всегда собственный номер
ближайшего вышестоящего автомата/БП.

Два разных по форме случая (оба — один и тот же механизм, просто с разной
«глубиной» источника):

1. **Автомат висит прямо на сыром выходе БП** (нет входящего имени потенциала,
   БП — не пронумерованная сущность): `-2QF30` (вход — сырой `L1+` от `-2G1`,
   без номера) → выход `30L+`. Номер = **собственный номер автомата**, буква —
   как есть у EPLAN. Один номер, без приставки.
2. **Автомат запитан от уже пронумерованного рельса**: `-2QF11` (вход — рельс
   `1L1`, уже пронумерованный — это выход `-2QF1`, главного автомата-ввода) →
   выход `1L11`. Номер = **унаследованная ведущая цифра от входящего рельса**
   (`1`, от `1L1`) + буква + **собственный номер автомата** (`11`). Два числа.

Автомат-ввод `-2QF1`/`-3QF1` сам попадает под случай 1 (его вход — сырые
L/N от внешнего кабеля, без имени потенциала): номер = его собственный номер
(`1`) + буква → `1L1`/`1N1`. То, что в обоих шкафах (ET101 и ET102) это число
совпадает (`1`), — не совпадение константы шкафа, а то, что автомат-ввод в
каждом шкафу по проектной конвенции всегда локально называется «...QF1»;
префикс шкафа (`2QF1` / `3QF1`) в имя потенциала не просачивается.

`M`/`PE` по тем же листам **не ветвятся по автоматам** — у всех веток `30L+`,
`31L+`... общий минус `1M`. Для PE отдельной работы не нужно: правило `PE` уже
существует и не требует номера (`Template = "PE"`, константа).

## Направление обхода: вход/выход

Подтверждено по схеме: клеммы `2, 4, 6` (и `?T?`) — выход автомата/контактора/ПЧ
(к нагрузке), `1, 3, 5` — вход (к источнику). Это уже используется в правиле
«Силовая цепь группы» (`Device = "??QF*;?QF*;??KM*;??U*"`, `Terminal = "2;4;6;?T?"`).
Новая логика переиспользует эту же конвенцию, отдельного способа определять
«вверх» не вводится: встретив вывод устройства на клемме из набора выходных —
переходим на «парную» входную клемму того же устройства (пара по номеру:
2↔1, 4↔3, 6↔5) и идём на узел, подключённый к ней, дальше вверх.

## Алгоритм

**Сужено относительно первой версии дизайна.** Изначально предполагался обход
через произвольную цепочку промежуточных (не-источник) устройств с лимитом
глубины — но ни в одном из проверенных по PDF примеров узел без имени не
отделён от автомата/БП посредником: generic-потенциал всегда сидит прямо на
выходной клемме самого устройства-источника. Делать многошаговый обход под
случай, которого не видели, значит гадать за пользователя — поэтому v1
поддерживает только то, что подтверждено: один шаг, без рекурсии. Если позже
на живом прогоне всплывёт реальная цепочка через посредника — это добавится
отдельно, тем же путём, что и остальные правила 1260 («уточняются по первому
живому прогону»).

Вход: узел (net) без собственного имени, но с generic-потенциалом (есть буква,
нет числа).

1. Среди концов узла ищем конец, чьё устройство подходит под **маску
   источника** (новое поле правила `SourceDevice`, по умолчанию
   `??QF*;?QF*;??U*;?U*;??G*;?G*` — автоматы, УЗО/ПЧ/УПП, блоки питания;
   настраивается в GUI, как остальные маски), и чья клемма — одна из парных
   выходных (`2`, `4`, `6`; парная входная — `1`, `3`, `5` соответственно).
   Не нашли такой конец — правило не срабатывает, узел остаётся без
   предложения (как сейчас при «нет правила»).
2. Нашли — смотрим узел, подключённый к парной входной клемме ТОГО ЖЕ
   устройства:
   - Входной клеммы в принципе нет провода (верх цепи, сырой источник —
     БП, внешний ввод) → результат = `{свой номер устройства}{буква}`,
     без второго числа (случай `30L+`).
   - На входе есть узел, и в нём уже есть конкретное (не generic) имя
     потенциала → **наследуем** его ведущую цифровую часть, результат =
     `{унаследованное}{буква}{свой номер устройства}` (случай `1L11`).
   - На входе есть узел, но потенциал на нём тоже generic/пуст (ещё не
     посчитан этим же правилом) → правило не срабатывает для текущего узла
     (не наследуем недосчитанное — безопаснее один раз не предложить номер,
     чем предложить неверный).

Буква берётся как есть из `Pin.Potential` текущего узла (не пересчитывается).
«Свой номер устройства» — полный числовой хвост DT после буквенного кода
(`2QF11` → `11`, `2QF30` → `30`, `2QF1`/`2G1` → `1`), группа шкафа (`2`/`3`) в
номер не входит.

### Область действия (scope)

Обход и проверка единственности имени — **в пределах одного `+CP.*`
(Location)**, не по всему проекту: подтверждено ET101/ET102 — одинаковые имена
потенциалов законны в разных шкафах (как `1M` уже сейчас законно повторяется
внутри одного шкафа — `SharedName`). Обход никогда не переходит границу
`+CP.*` (если опорный конец без маски-источника и без пары в пределах того же
Location — обход останавливается без результата, не уходит на другой лист
другого шкафа).

## Архитектура

Чистая офлайн-логика в `EplanCipMvp.Core/WireNaming/`, без обращений к живому
EPLAN — работает на данных, которые `WireNumbering.ReadAll` уже читает сейчас
(Device/Terminal/Location/Potential по каждому концу провода, `WireNets.Build`).
Новых вызовов EPLAN API не требуется.

- **`WireNetGraph`** (новый файл `WireNaming/WireNetGraph.cs`): по списку
  нетов (`WireNet`) строит индекс «устройство (Location+Device) → его клеммы →
  нет, подключённый к каждой клемме» (переиспользует уже распарсенные
  `WireEnd` через `WireNets.Ends`). Метод `ResolveSourceNumber(net, sourceDeviceMask,
  letter)` — один шаг алгоритма выше (без рекурсии), возвращает готовую строку
  номера или `null`, если под условие ничего не подошло.
- **`WireRule`**: новое поле `SourceDevice` (строка-маска, как остальные
  `Location`/`Device`/`Terminal`), пресет по умолчанию см. выше.
- **`WireRuleTemplate`**: новый токен `{Потенциал:источник}` — вызывает
  `WireNetGraph.FindSource` через контекст (который получит ссылку на граф) и
  рендерит результат по формуле из алгоритма. Используется в новом правиле
  пресета (добавляется в `WireRulePresets.Like1260()`, после правила
  «Канал ПЛК», перед «Силовая цепь группы» — туда, где сейчас `{Потенциал}`
  не применяется из-за generic-имени).
- **`WireNamingEngine.Preview`**: строит `WireNetGraph` один раз на весь
  проект (до цикла по нетам, аналогично `CoreAssigner.Assign`), передаёт в
  контекст рендера.
- **GUI (`WireNumberingPanel.cs`) и Web**: новая колонка «Источник (вход)» в
  таблице правил (аналогично остальным маскам — добавляется в `RuleColumns`,
  `FillRulesGrid`, `TryReadRulesFromGrid`) — это и есть гибкость, о которой
  просил пользователь: маску-источник можно поменять в интерфейсе без
  пересборки программы, если обнаружится устройство другого типа, которое
  тоже должно считаться источником.

## Защита от ошибок

- Как и для остальных правил — это предложение, не запись: пользователь видит
  строку предпросмотра, снимает галочку, правит номер руками при несогласии
  (ничего не меняется в существующем workflow «Считать → Предпросмотр →
  Записать»).
- Обход — ровно один шаг (п.1-2 алгоритма), без рекурсии: циклов по
  построению не бывает, лимит глубины не нужен.
- Конфликты между предложенными именами (в т.ч. с существующими дублями) —
  без изменений, через уже существующий `MarkConflicts`/Фикс 2 из
  `2026-09-25-wire-numbering-conflict-resolution-design.md` (новое правило
  просто участвует в общем пайплайне наравне со старыми).

## Проверка

Автотесты Core (`WireNamingSelfTest.cs`), без реального EPLAN:

1. Прямое подключение к сырому источнику: автомат на выходе БП без входящего
   имени → `{свой номер}{буква}` (случай `30L+`).
2. Автомат, запитанный от уже именованного рельса → наследование + свой номер
   (случай `1L11` от `1L1`).
3. Узел без подходящего устройства-источника среди концов — правило не
   срабатывает, узел без предложения (не падает, не гадает).
4. Входная клемма устройства-источника есть, но на ней тоже generic/пустой
   потенциал (сосед ещё не посчитан) — правило не срабатывает для этого узла.
5. Два независимых шкафа (`+CP.ET101`, `+CP.ET102`) с одинаковыми DT-суффиксами
   автоматов и одинаковыми ожидаемыми именами потенциалов — подтверждает
   локальность по Location, обход не путает шкафы.
6. `M`/`PE`: общий минус на несколько веток — один и тот же номер, не дубль
   (переиспользует существующую логику `SharedName`/`LooksLikePotential`).

Сборка и живой прогон — как у остальной фичи: против EPLAN 2.9 DLL, первый
прогон на копии проекта.

## Вне рамок

- Изменение формата `wire-numbering-rules.json` сверх одного нового поля
  `SourceDevice`.
- Автоматическое разрешение коллизий между предложениями этого правила и
  существующими — работает через уже реализованный Фикс 2 без изменений.
- Любая попытка учитывать фазировку/реальную электрическую топологию за
  пределами того, что уже видно из Device/Terminal/Location — алгоритм
  работает только с тем, что есть в модели проводов сейчас.
